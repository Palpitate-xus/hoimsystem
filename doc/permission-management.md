# 权限管理

入口：**系统管理 → 权限分配**，地址为 `/#/system/permission`。页面包含“用户权限”“角色权限”和“权限审计”。

## 管理范围

| 登录身份 | 可配置的策略 | 账号操作 |
| --- | --- | --- |
| 管理员 `admin` | 普通岗位及其用户 | 调整普通账号角色、重置密码、删除账号 |
| 超级管理员 `super_admin` | 管理员、普通岗位及其用户 | 管理其他管理员账号，可分配超级管理员角色、重置其他超级管理员密码 |

超级管理员策略固定保留，供权限恢复使用。当前登录账号的角色调整和删除按钮禁用；账号管理操作同时受各自接口权限控制。

## 配置角色与用户

1. 在“角色权限”选择岗位并打开“配置权限”。
2. 选择“继承默认权限”或“自定义权限”。按业务模块筛选，再搜索名称、方法或路径，逐项勾选；“选中本页”“取消本页”只作用于当前页。
3. 为医生或科室主任选择数据范围，然后保存。
4. 在“用户权限”找到账号，打开“用户权限”，选择继承角色或进一步缩小个人权限。
5. 在“权限审计”查看操作人、对象、时间及配置前后的内容。

接口权限取三者交集：**固定岗位业务资格 ∩ 角色策略 ∩ 用户策略**。角色可配置项来自该岗位的业务资格；用户可配置项来自当前角色已授予的集合。具体患者、就诊、来源及执行状态由相应业务的对象规则核对。

| 设置 | 角色策略 | 用户策略 |
| --- | --- | --- |
| 继承，对应 `allowed_permissions: null` | 使用岗位默认权限 | 使用当前角色有效权限 |
| 自定义，对应权限码数组 | 只授予选中的岗位权限 | 只保留角色权限中选中的项目 |
| 自定义且清空，对应 `[]` | 不授予该角色业务权限 | 不授予该用户业务权限 |

本人权限查询和退出等基础会话操作保留。

## 权限项目

每个接口按 **HTTP 方法 + 路由模板** 单独配置。同一路径的不同方法分别授权，例如：

| 权限码 | 操作 |
| --- | --- |
| `GET /api/medicalRecord/getList` | 查询病历 |
| `POST /api/medicalRecord/create` | 新建病历 |
| `POST /api/medicalRecord/sign` | 签署病历 |
| `GET /api/dataImportExport/export/{entity}` | 导出指定类型数据 |
| `AI patient_summary` | 使用患者全景摘要能力 |

模板中的 `{entity}`、`{id}` 等参数代表接口匹配规则。数据对象是否可访问，在请求时按实际记录核对。查询、审批、导出与 AI 能力可以分别保留或撤销。

### 患者目录列表字段

以下三项作用于 **`GET /api/patientManagement/getList` 患者目录列表**：

| 权限码 | 返回内容 |
| --- | --- |
| `FIELD patient_list.identity` | 岗位具备完整身份查看资格时返回完整身份证与电话；撤销后返回掩码 |
| `FIELD patient_list.address` | 返回地址；撤销后该字段为空 |
| `FIELD patient_list.allergy` | 返回过敏史；撤销后该字段为空 |

病历、处方、导出和 AI 来源等其他接口分别使用各自的接口权限、患者范围与对象访问规则。

## 临床数据范围

| 选择 | 行为 |
| --- | --- |
| 既有业务范围 `existing` | 沿用该岗位及接口原有的患者、本人或科室访问规则 |
| 本人接诊患者 `assigned` | 医生或科室主任仅访问与本账号医生身份建立预约、挂号、病历、处方或住院关系的患者及其关联记录 |

`assigned` 同时约束关联明细、查询统计和写入。账号需要关联医生档案；没有接诊关系时，范围内患者列表为空。

角色策略或用户策略任一选择 `assigned`，最终范围即为 `assigned`。用户配置中显示“当前生效范围”，可核对角色与个人设置共同产生的结果。

## 停用、版本与生效

“停用访问”位于用户权限配置中。保存后禁止该账号登录和受保护访问，并使已有会话失效。恢复账号时关闭该开关并保存，用户重新登录。

每次策略修改使用当前版本保存。其他管理员已修改同一策略时，服务器返回 **409**，页面保留草稿并提示冲突。点击“重新加载”，核对最新配置后再保存。

后端按当前策略校验每次受保护请求，越权返回 **403**。菜单与直达页面根据有效权限过滤；管理按钮按操作权限启停。权限变更通过 SSE 更新当前会话，403 也会触发权限快照刷新，原请求不自动重放。

AI 功能单独配置 `AI <功能键>` 权限。任务创建、执行以及受保护来源和结果读取均核对当前权限；撤销后，相应后续操作被拒绝。AI 管理中心继续维护模型、Prompt、知识及用途授权。

## API 与升级

| 方法与地址 | 用途 |
| --- | --- |
| `GET /api/access/catalog` | 查询岗位、接口、AI 能力和字段权限目录 |
| `GET /api/access/me` | 查询当前账号有效权限、版本及页面访问状态 |
| `GET /api/access/policies/{kind}/{key}` | 读取角色或用户策略 |
| `PUT /api/access/policies/{kind}/{key}` | 按 `expected_version` 保存策略 |
| `GET /api/access/audit` | 分页查询权限变更记录 |

`kind` 为 `role` 或 `user`。角色的 `key` 为岗位标识，如 `doctor`；用户的 `key` 为用户 ID。保存字段为 `expected_version`、`allowed_permissions`、`data_scope` 和 `disabled`；角色策略的 `disabled` 保持 `false`。

升级数据库时，在后端虚拟环境中执行：

```bash
cd fastapi_be
python -m app.db_migrate
alembic current
```

当前迁移头为 **`20261029_session_binding`**，包含权限策略、变更审计和账号会话绑定。JWT 绑定用户 ID 与 `auth_subject` 账号唯一标识；删除后重新创建同名账号会取得新标识。旧版本登录令牌在升级后需要重新登录一次。

接口岗位资格见 [API 访问矩阵](api-rbac-matrix.md)，部署流程见 [部署手册](installation-guide.md)。
