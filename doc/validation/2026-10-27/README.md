### 有限重试

超级管理员配置文本服务的最多尝试次数（含首次，1–3）；新服务默认 3，升级已有服务保留 1，旧冻结快照按原字节和单次策略读取。专用附件服务不重放。仅连接建立失败或临时 429/502/503/504 进入重试，共用原总超时；已交付正文、结构或引用错误不重试。有效 Retry-After 超过本次等待上限或剩余预算即停止，重发前重新核对当前租约、账户、配置、Prompt 和来源授权。不能证明前次用量时，保留未知费用。

[真实 HTTP 故障注入](llm-retry-http-campaign.json)覆盖 63 功能 × 两种协议：126 个恢复场景都在前两次 503 后第三次成功；126 个持续失败场景都恰好调用 3 次并失败。原先两个嵌套网关错误发出 5 次的缺陷已修复并重测。该批证据绑定当时源码，之后新增的 Retry-After 和实时权限检查范围在[源码跟进记录](llm-retry-http-source-followup.json)单独说明；最终传输、真实 worker、原生回执、撤权和迁移的完整 5 文件 **110 项通过**，版本 `80abc65`。最终版的其他完整原生任务文件及最新 HTTP 任务复验单独归档，不将不同源码测量混为一次。

[真实 PostgreSQL 升降级](retry-postgresql-migration.json)使用旧不可变镜像创建的 266 表独立 schema：从精确旧 head 应用两条新迁移，原 Provider 变为单次、新 SQL 默认三次，原行及 JSON 字节保持不变；未知 token 的 SQL NULL 可保存，含未知用量时降级明确拒绝且不改数据，恢复原已知计数后可回退。7 项断言通过，临时 schema 已删除。

后续[完整原生任务回归](retry-native-regression.json)执行 54 文件、1,092 项，1,087 通过、5 项原断言失败；4 项仍按旧策略期望 503 只调用一次，另 1 项把新可选字段误算为旧必需字段。按新契约修正后，对全部失败文件及变更的存储、运行时、回执、传输层完整复验 **15 文件、418 项通过**。原 1,092 项期间的 4 个 AI 源文件变动单独保存；它不是一次全程同源码的最终全绿运行。

同一最终轮的[12 原生域 × Chat/Responses](retry-twelve-native-workers.json) **24 项全部通过**，另有科研变量配置完整文件 15 项通过。所有任务经真实 shared worker、现有来源服务和受控 503/503/200 传输，核对接受结果、当前来源、独立回执与未知用量。新补的 7 域还逐行比对原业务数据；正常追加的操作审计与业务修改分开。文档、评价、账目、双版本文档、药品说明书原先强制“成功必须已知 token”的门已修复；药品重试前使用实际 StoredTask 重新授权。版本 `3cce378`、`24bc5ee`、`bd75512`。

## 事务并发

先执行 8 类、每类 20 请求的真实 HTTP 竞争，发现号源返还、待付单、床位和 PostgreSQL 发药问题。复验扩大为 11 类，各 20 请求，全部通过；重复预约竞态也在复验中暴露并修复，没有以某一次偶然通过替代竞争控制。

[原始失败](concurrency-before.json)与[11 类复验](concurrency-eleven-cases.json)包括最后号源不超卖、重复预约一次、并行取消逐一返还、待付单唯一、现金支付/退费一次、同床单占用、独立入院编号唯一、同患者单入院、同处方单发药、同执行单次给药。之后又扩展患者现场挂号与窗口挂号竞争，作为最终版本补充验收。

最终 13 类验收第一次在窗口挂号发现真实遗漏：[20 请求产生 10 条重复挂号](concurrency-window-before.json)。将患者锁放到实际创建事务、移除身份预览 GET 上多余的锁后，[20 并发](concurrency-thirteen-20.json)与[50 并发](concurrency-thirteen-50.json) **13 类均通过**，合计 910 次竞争请求，另有准备请求。窗口相关 6 个完整文件 81 项通过，包含真实 PG 的身份查询不阻塞、持有患者锁阻止创建、窗口之间及窗口与患者端混合竞争，挂号与收费各仅一条。

[实际库存过载](inventory-backpressure-http.json)中，另一 PG 事务持有库存锁，合法医生开方在约 15.024s 后收到 503 / Retry-After: 1，处方、费用、药品明细均为零、库存未变；释放锁后独立的新请求 66.6ms 成功。系统没有自动重放业务写入。

这些请求检查 HTTP 状态、业务 `code` 和数据库行数、状态、号源、库存及账本，业务冲突允许正常拒绝，HTTP 500 不算正常冲突。此处验证事务正确性，吞吐和延迟采用独立负载窗口测量。

## 性能测量条件

实际运行的是 PostgreSQL **17.2**，不是 Compose 默认的 16：两处镜像源获取 16 超时后，使用本机已有 17.2 并记录真实版本。API 4 个 Gunicorn worker，API 和数据库各限制 4 CPU / 4GiB；主机为共享 48 核机器，其他用户任务未停止。

[实际镜像与源码摘要](load-image-manifest.json)保存运行镜像的 686 个 Python/依赖源文件哈希和软件版本。负载启动后仓库继续进行重试功能开发，仓库 HEAD 不能替代运行镜像版本；最终新版另做对照验证。

小、中、大档分别为 1,000 / 10,000 / 100,000 患者，各 5,000 / 50,000 / 500,000 条处方、明细、费用、病历历史。三档各测 1 / 10 / 50 / 100 / 200 用户，另测持续负载和更高压力。用户包含 0.2–0.8s 思考时间，不等于同数同时在途请求。负载约 96% 读取、4% 实际预约/处方写入。

每轮登录、目标发现、爬升和预热与正式时间窗分开；报告同时保留请求生成窗口、在途排空时间和保守吞吐。逐轮观察主机负载、容器 CPU/RSS、数据库连接、事务与锁，并核对业务写入行数守恒。短时结果不能作为生产 SLA。

另做同镜像、同 API 4 核、同数据库 4GiB、只将 PostgreSQL 从 4 核提高至 8 核的[单项对照](load-pg-cpu-control.json)：大档 100 用户 60 秒，10,333 次请求、零失败，P95 **510 → 170ms**，保守 RPS **149.46 → 171.93**（约 +15%）；随后恢复数据库 4 核。这支持数据库 CPU 是该条件下的一个瓶颈，不能由此推断所有场景线性扩容。

以上原冻结版本的失败不会被之后 503 处理覆盖。503 只明确表达过载、回滚和重试边界，仍计为压测失败，也不表示吞吐容量问题已消失。最终新版的事务竞争和负载对照另行绑定新镜像记录。
